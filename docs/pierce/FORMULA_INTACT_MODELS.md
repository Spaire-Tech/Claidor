## Method — how formula integrity was established

Applies to both models. Reproduce with
`corpus-verify/analyze_xlsx.py`.

1. **Download the binary.** `curl` to disk, then `file` to confirm the
   magic bytes really are `Microsoft Excel 2007+` (an OOXML ZIP), not
   an HTML error page saved under an `.xlsx`/`.xlsm` name. Both files
   passed; several fetch attempts in this run did return HTML under a
   spreadsheet filename, so this step is not optional.
2. **Parse the OOXML parts directly, not through a convenience API.**
   Each `xl/worksheets/sheetN.xml` is streamed with `iterparse` and
   every `<c>` (cell) element is classified:
   - `<c>` with an `<f>` child → **formula cell**
   - `<c>` with `<v>`/`<is>` but no `<f>` → **hardcoded cell**
   - `<c>` with neither → not counted as populated
   This is ground truth from the file format. A library that returns
   cached values would report a stripped workbook as fully populated;
   reading `<f>` presence cannot.
3. **Read the workbook part** `xl/workbook.xml` for sheet names, sheet
   `state` (`hidden` / `veryHidden`), `<definedName>` entries (named
   ranges) and `<calcPr>` (calculation settings, including whether an
   `iterate` attribute is present).
4. **Check the package** for `xl/externalLinks/externalLink*.xml`
   (external workbook links) and `xl/vbaProject.bin` (macros).
5. **Classify formula targets**: a formula string containing `!` is a
   cross-sheet reference; a real external-workbook reference is an
   indexed book token matching `\[\d+\]`. A bare `[` is *not*
   sufficient — it is usually a structured table reference such as
   `Table[[#This Row],[Col]]`, which is internal. The
   `xl/externalLinks/` part count is the authoritative signal and is
   reported alongside.
6. **Independent cross-check, bypassing the parser entirely.** For
   any file, unzip and count raw formula elements:

   ```bash
   unzip -o -q FILE.xlsm -d /tmp/x "xl/worksheets/*.xml"
   cat /tmp/x/xl/worksheets/*.xml | grep -o '<f[ >/]' | wc -l
   ```

   On the Packt file this returns **2,973**, exactly matching the
   parser. The same command returns **0** on three of the four
   rejected SFT workbooks, which is how the method was shown to detect
   formulas when they exist and report zero only when they genuinely
   do not.
7. **Locate the formulas, do not just count them.** Formula density is
   computed **per sheet**, and specifically on the sheets carrying the
   financing and cash-flow logic. A whole-file percentage is not
   sufficient evidence: one rejected candidate in this run held 169
   formulas that were *all* on a single `Databook` sheet, with zero on
   `CalcM`, `CalcSA`, `CashFlowSA`, `Ratios`, `Drawdown schedules` and
   `Repayment schedules`. **Apply this same per-sheet test to every
   future corpus candidate.**

Known bound on the method: the project-finance content check in
§ 3 matches **label text**, so it evidences that a concept is *named*
in the workbook. On its own it proves nothing about implementation —
the rejected value dumps scored 18/18 on labels while containing no
logic at all. Throughout this document, a concept is marked VERIFIED
only where a **formula** implementing it was read; where only a label
was found, that is stated explicitly.

## 5. Swens relevance

- It is the **only obtained file containing genuine debt-sizing logic
  under live formulas** — sculpting to a target DSCR, an annuity
  alternative via `PPMT`, DSRA reserve accounts and a CFADS line.
  This is exactly the structure the engine's debt-schedule and ratio
  reckoning must recognise, and it can be used to assert that
  recognition against real formulas rather than a constructed fixture.
- **Scale and cross-link stress test.** 782,093 formulas and 255,064
  cross-sheet references over 72 sheets exercise precedent tracing,
  period/column alignment and performance at a size no hand-built
  fixture reaches.
- **Paired-structure asset.** The parallel PSC and P3 stacks
  (`PSC Financing` / `P3 Financing`, `PSC Reserves` / `P3 Reserves`,
  `PSC CWF` / `P3 CWF`) are two near-identical model families inside
  one workbook. That is directly useful for the sibling/family
  detection and comparison work, and for testing that structurally
  similar blocks are not falsely collapsed.
- **Intake edge cases in a single file**: macro-enabled `.xlsm`,
  structured table references, 144 named ranges, runtime sheet
  hide/unhide via VBA, and a 12MB payload. Good adversarial input for
  the upload path.
- **Time-series shape**: financing rows run column `J` to `BQ`
  (≈60 periods) with a row total in column `H` — a clean case for
  period-axis detection and for the sibling-total exemption rules.

## 6. Limitations

- **It is an educational/analytical tool, not a real closed
  transaction.** It models a hypothetical project for value-for-money
  comparison, so it will not exhibit the negotiated idiosyncrasies,
  the layered revision history, or the multi-author mess of a live
  deal model.
- **Roughly half the workbook is benefit-cost analysis, not project
  finance.** The largest sheets by cell count are `Pure Risks`
  (107,720 populated), `Traffic` (102,121), `Benefits Existing
  Traffic` (69,357) and `Benefits Per Vehicle` (48,726). The
  project-finance core is concentrated in about 11 sheets totalling
  roughly 60,000 populated cells. Do not treat the 796k figure as
  796k cells of project-finance logic.
- **Licence NOT VERIFIED** — see § 1. This blocks redistribution
  inside a committed corpus until confirmed; the file is re-fetchable
  by URL in the meantime.
- **VBA was not decompiled.** Module *names* were read from
  `vbaProject.bin` strings; the macro source was not extracted or
  analysed. If macros mutate cell contents on open, that is unassessed.
- **Circularity was not traced.** The stored setting (`iterate`
  absent) was checked and is off; no dependency-graph analysis was run
  to confirm the workbook is actually acyclic.
- Values were not recalculated. The file was inspected statically;
  no claim is made that its cached values match what Excel would
  compute.

  exhaustively.** Opening balance → drawdown → repayment → closing
  balance, with interest on the opening balance and debt service as
  principal + interest. This is the reference shape for asserting the
  engine's debt-schedule recognition without a 12MB file in the loop —
  a fast fixture for the golden-master gate.
- **The only redistributable model obtained.** MIT licence means it
  can be committed to the repository, unlike everything else here.
  That makes it the natural default fixture for CI and for the
  corpus gate.
- **Dense cross-sheet linking at readable scale**: 1,643 cross-sheet
  references over just 4,088 populated cells, in a workbook a person
  can read end to end and hand-verify. Ideal for building
  precedent-tracing ground truth, because the correct answer can be
  established by eye.
- **A clean three-statement build** (`P&L`, `Balance Sheet`, `CFS`)
  with a balance check available — useful for flow-vs-stock and
  statement-articulation checks.
- **Known-good input/calculation separation.** Inputs are isolated on
  two sheets at 11.66% and 2.16% formula density while every
  calculation sheet sits above 72%. This is a positive control for
  any heuristic that classifies sheets by role, and a baseline against
  which the value-dump signature is unmistakable.
- **A working scenario mechanism** (`INDEX` against a single selector
  cell) — a compact test case for scenario/switch detection.

## 6. Limitations

- **It is a teaching model, not a transaction model.** It is a book
  companion file; it has none of the revision history, negotiated
  structure or multi-author inconsistency of a real deal model.
- **It is small**: 10 sheets, 4,088 populated cells, 2,973 formulas.
  It cannot serve as a scale or performance test.
- **NO DSCR ANYWHERE.** This was verified rather than inferred: a
  `grep` over the whole shared-string table returns only "Debt
  Service" / "Debt service" — the cash-flow line — and **no** DSCR,
  ADSCR, LLCR, PLCR or cover-ratio label. The `Ratios` sheet computes
  Project IRR and Equity IRR only. The model has CFADS and debt
  service as separate lines but never divides one by the other.
  **Do not use this file to test DSCR or cover-ratio logic.**
- **No debt sizing in the project-finance sense.** Funding is an
  equity-first cascade to a fixed gearing input. There is no
  ratio-driven sizing, no sculpting, no repayment solve.
- **No reserve accounts** — no DSRA, no maintenance reserve.
- **No named ranges (0)** and no macros, so it exercises none of those
  intake paths.
- **Jurisdiction not stated** in the workbook; only the `k£` currency
  is evidence. The "Express Fiji" case name is **not** in this file.
- **27.27% of populated cells are hardcoded.** This is
  well-distributed (inputs and date axis) and not a defect, but any
  threshold-based intake gate must not be set so high that it rejects
  a legitimately input-heavy model of this shape.
- Values were not recalculated; the file was inspected statically.

# 7. CORPUS RECOMMENDATION

### FHWA P3-VALUE 2.3 — **KEEP**

782,093 formulas at 98.20% of populated cells, with only 1,635
hardcoded numeric cells in the entire workbook, and 97–99% formula
density sustained across all eleven financing, reserve, depreciation
and cash-waterfall sheets. It contains real debt-sizing mechanics
under live formulas — sculpting to a target DSCR, a `PPMT` annuity
alternative, DSRA target-balance and deposit/withdrawal logic, and a
CFADS line — which no other obtained file has. Its scale (72 sheets,
255,064 cross-sheet references), its macro-enabled packaging, its
structured table references and its paired PSC/P3 model families make
it the corpus's stress test as well as its project-finance reference.

### Packt / Meta Brains — **KEEP (NARROW)**

2,973 formulas at 72.73% of populated cells, with every calculation
sheet between 72% and 87% and the hardcoded cells correctly confined
to the input and time-axis sheets. It carries the canonical debt block
(opening balance, drawdown, repayment, closing balance, interest on
opening balance, debt service), a three-statement build, working tax,
dividend and scenario logic, and both IRRs. It is narrow — small, no
DSCR, no reserves, no named ranges, no sizing — but it is MIT
licensed, and therefore the only model here that can be committed and
redistributed, which makes it the default fast fixture.

**These are the first two models that have been empirically verified
to contain substantial live financial-model formulas. They should be
treated as confirmed formula-intact corpus members.**

calculation sheet — while carrying live-model sheet names, 577 named
ranges, intact VBA and the complete project-finance vocabulary in its

**Why they were not obtained.** `ppiaf.org` and `www.ppiaf.org` sit
behind a Cloudflare bot challenge that returned HTTP 403 with a
`Just a moment...` interstitial to every client available in that
environment: `curl` with default headers, `curl` with a full Chrome
header set over HTTP/2, `wget`, Python `urllib`, and Playwright-driven
Chromium. The 403 came from the origin, not from the network proxy —
the challenge HTML arrived in the response body. Two fallbacks also
failed: `web.archive.org` is blocked by that environment's egress
policy (the availability API on `archive.org` confirms a HTTP 200
snapshot of the railways `.xlsm` exists at timestamp
`20190919192431`, but content fetches were reset mid-tunnel), and
Chromium could not egress at all, failing with `ERR_CONNECTION_RESET`
even against `example.com`. A World Bank documents API search returned
the toolkit **PDFs** but no spreadsheet; `ppp.worldbank.org` is behind
the same Cloudflare block.

**What the next agent should do.** Obtain these three from a network
that can reach the host — an ordinary browser session will clear the
Cloudflare challenge — or from an environment whose egress policy
permits `web.archive.org`. Then run them through the identical
procedure in **Method** above, including the per-sheet formula-density
test and the raw `grep -o '<f[ >/]'` cross-check. Note that two are
legacy `.xls` (BIFF, not OOXML), so the OOXML parser in
`corpus-verify/analyze_xlsx.py` will **not** work on them: `.xls`
needs a BIFF path (`olefile` plus FORMULA-record parsing, or
LibreOffice conversion — and if converting, verify formulas survive
the conversion before trusting any count).

These three are the only remaining candidates that could add a second
and third **sector** (rail, port) to a corpus currently holding only
highway/toll-road models. Classify them only after opening them.
