Grok Bot Detailed Overview

## 1. What Grok Bot is

Grok Bot is a desktop assistant product: a chat-first agent that can act on the user's behalf across their computer, a dedicated agent computer ("my computer" / the box), connected services (connectors), the web, and multi-agent teamwork.

Each bot is a named agent with its own chat, persona (name, title, description, avatar), memory, routines, and settings. Users can run many bots; a Chief of Staff–style agent can create/manage teammates and pull the user in for decisions.

Core design principles visible in the runtime:

* Act by default — decide and proceed unless the action is consequential/destructive, truly ambiguous, or needs a fact only the user knows.
* Chat is the UI — results, questions (choice cards), attachments, connector prompts, and approvals surface in conversation.
* Real tools, not pretend — no fabricated metrics, menus, click-paths, or source attributions; if a path isn't known, say so.
* Safety gates — Auto-review on risky tool calls; local-execution approval for the user's registered machines; OS permission dialogs for protected resources.

## 2. Product surfaces

### 2.1 Desktop app

Settings are opened via the sidebar account button (bottom-left), Cmd+, or the command palette ("Open settings"). There is no gear icon / macOS Preferences item.

**Settings tabs**

* General — account (Sign In with Cursor / Sign Out), theme (Follow System / Light / Dark), language, microphone, hardware acceleration, network debugger, notification sounds, timezone, local execution, Auto-review / Auto-review rules, security keys, agent defaults.
* Computer — registered user machines; box recovery via Update / Reset (see §4).
* Usage & Billing — included usage, on-demand, plan controls (when enabled for the account).
* Updates — Update Track (Stable / Nightly), Check for Updates (app). Distinct from updating the agent computer.

**Per-agent info pane** (click agent name in chat header, or Cmd+Shift+I)

* Live preview of that agent's computer (click for full screen).
* Routines list.
* Channels (when channel connectors are available / connected).
* Members (in group chats).
* Gear → per-agent settings: avatar, name, title, description, notifications.

**Agent lifecycle (user)**

* Create agents (and optional sidebar sections).
* Delete: sidebar → right-click agent → Delete (permanent; removes agent + transcript; confirm). No archive.

Deep links exist for many settings rows (e.g. local execution, update computer, theme) so the agent can point the user straight to the right control.

### 2.2 Chat

Primary interaction is 1:1 chat with an agent. Capabilities include:

* Text replies (often short, multi-bubble).
* Choice cards (widgets) — structured questions with selectable options; optional multi-select, custom free text, danger/primary styling, dismiss-on-move-on.
* Attachments — files/media (local `file://` or https); images can inline under text.
* Voice memos — playable spoken clips when the user asks for a memo.
* Secret requests — masked credential capture into env vars (never paste secrets into chat).
* Connector cards — host-authored connect/auth UI for MCP connectors.
* Cursor cloud agent cards — open a cloud coding agent from chat.
* Threaded replies for secondary bulk (digests/progress), with key results kept in the main chat.
* Reactions (emoji tapbacks) for lightweight acknowledgment.
* Reference chips linking back to earlier messages.

Outbound messaging platforms can be connected as channels; inbound wakes the agent with channel context (see §8).

### 2.3 Group rooms

Local group chats / channels can host multiple member agents. Room turns follow room-specific rules (group-chat skill). Agents can also post privately to the user's DM from a room turn when appropriate.

## 3. Agents, teammates, and Chief of Staff

### 3.1 Agent identity

Each agent has:

* Name (chat title), title (role chip), description, avatar (shape/color or custom image).
* Optional hide-from-sidebar (still reachable via Hidden chats / Cmd-K).
* Notify-on-updates toggle.
* Durable memory (profile / log / note tiers; agent-scoped or shared user-scoped or project-scoped).
* Routines and skills (skills are a global library; see §7).

### 3.2 Multi-agent

* CreateAgent — spin up a teammate in an optional sidebar section.
* UpdateAgent — edit another agent's name/description safely.
* SendToAgent — async messaging to one agent or a group channel (like texting; replies arrive on later turns).
* CreateChannel / UpdateChannel — named group chats with member seating.
* Agents cannot delete other agents or channels; only the user can delete from the sidebar.
* Fan-out to many agents is gated: do it when the user asks, or propose first — avoids burying the user in reply storms.

A Chief of Staff agent is oriented toward managing the fleet and escalating decisions to the user.

## 4. Computers: the box and the user's machines

Grok Bot has two computer concepts:

### 4.1 The agent computer ("my computer" / the box)

* One persistent Linux machine shared by all of this user's agents (same filesystem, tools, browser logins).
* Each agent gets its own desktop and browser window on that shared machine (desktops are not shared across agents).
* Scratch: `/workspace`. Profile/memory/routines/skills/channels live under `/home/box`.
* Tools: Shell, structured Read, Screenshot (read-only), browser/desktop via `computerUse` subagent.
* Can install packages, run code, generate files, keep logins across turns.
* Runtime: local Docker (dev) or brokered anyrun pod (shipped default). Health via `box-doctor`.
* Recovery: Update Grok Bot's Computer moves to a fresh instance keeping files/logins (reinstall software after). Reset restores last snapshot and can lose recent work — prefer Update.

### 4.2 Registered user computers

* User machines registered with the app (e.g. a Windows PC labeled in-app).
* Shell/Read/file copy with `machineId` run on that machine and require local-tool / local-execution approval.
* Messages can carry `[Sent from machine <id>]`; default to that machine when the user doesn't specify.
* CopyToBox / CopyFromBox move files between a registered machine and the box.
* OS consent dialogs still apply for protected folders, mic, camera, screen recording, etc. — attempt the action and let the OS ask.

Hard rule: repository / coding project work goes to a Cursor cloud agent, not random checkouts on the box or user machine (unless an explicit code-changes skill exception applies).

## 5. How work gets done (tooling model)

### 5.1 Direct tools (high level)

* Chat delivery to the user.
* Shell / Read / file transfer (box or selected machine).
* Web search / fetch.
* Memory, routines, skills, profile, settings, projects, avatar updates.
* Plugin/connector lifecycle (search, install, auth, status).
* Cloud agents for repos.
* Subagent orchestration (Task / message / stop / check).
* Forms (`request_user_form`) and box handoff (`request_box_help`) for logins/manual steps.
* Image generation when asked for a visual asset.
* Feedback to the product team when the user asks.

### 5.2 Subagents

Background workers keep the main chat responsive:

* executor — general-purpose workhorse (multi-step investigation, research, long command sequences).
* computerUse — drives the box desktop/browser (one at a time; shared screen).
* watchVideo / videoReview — video understanding (agents cannot "watch" video bytes themselves).

Non-trivial work is delegated; the main agent delivers results to the user. Stop/cancel from the user stops running children and related background shells.

### 5.3 Escalation order

Prefer: existing context → connector → web → signed-in browser on the box → desktop GUI → ask the user. Don't use the browser as a side door around a broken connector the user expects.

## 6. Connectors (MCP plugins)

Connectors are integrations (Notion, Slack, Linear, GitHub, etc.) packaged as plugins with MCP servers and often skills.

Lifecycle:

1. Search catalog.
2. Get plugin detail (fields/secrets).
3. Confirm install with a choice card.
4. Install; host shows connect/auth card when needed.
5. Authenticate / reconnect as status requires.

Connected tools become live CallDynamicTool surfaces. Notion (as used in this workspace) is an example: search, fetch, private draft page creation, databases, comments, and more — with `creation_mode: "draft"` for workspace-private pages.

If no catalog match: optional remote MCP URL / local command add path; otherwise say it's unavailable (or use browser for a logged-in site).

## 7. Skills

Skills are a global shared library of reusable procedures ("use this when…"). Types:

* Cursor-managed skills (read-only): e.g. routines, box-desktop, code-changes, scheduling, shopping, flights, food ordering, restaurant booking/recommendations, rideshare, purchases, send-on-behalf, channels, group-chat-turns, in-chat-forms, no-connector-fallback, add-connector, skill-authoring, learn-from-demonstration, export-bot-template.
* User-created skills (editable via skill write/delete).
* Plugin skills shipped with connectors.

Agents are instructed to read and follow the relevant skill before acting in that domain (e.g. don't open a delivery app before the food-ordering skill).

Demonstration → skill: screen recordings can be turned into reusable skills (`learn-from-demonstration`).

## 8. Routines

Routines = saved prompt + trigger, running even when the user is away.

**Triggers**

* Cron / schedule (`@daily`, `@every 2h`, explicit cron; min interval 5 minutes).
* Event listeners: Slack, GitHub, Origin, Microsoft Teams, Linear, Sentry, PagerDuty, webhooks, and grouped listeners.

Prefer event listeners over polling when the event shape exists. Creating/changing routines may require user confirmation. Pause / resume / delete / update in place (history preserved).

Wakes are silent scheduler cues; the agent surfaces results in normal voice (or stays quiet if the prompt says so when nothing changed).

## 9. Memory and projects

**Memory tiers**

* profile — foundational, kept in mind.
* log — dated history.
* note — fades fast.

**Scopes**

* Agent-only.
* Shared user memory (visible to all of the user's assistants).
* Project shards (project slug).

Agents can search older facts via RecallMemory; writes go through controlled update APIs (deduped).

Projects can be created/joined/left; useful for scoped collaboration and memory.

## 10. Code and Origin

When the user asks for apps, features, fixes, refactors, or repo investigation:

* Follow the code-changes skill.
* Use Cursor cloud agents for repository work.
* Origin / `origin` CLI paths are part of that skill surface.
* Cloud agent artifacts/PRs are the handoff mechanism (don't attach VM-local artifact paths that won't render).

## 11. Domain automations (built-in skills)

Out-of-the-box workflows (each gated by its skill before acting):

* Calendar / scheduling / availability.
* Shopping (Amazon and retail).
* Flights (search, book, check-in, boarding pass).
* Food delivery / pickup.
* Restaurant booking and recommendations.
* Rideshare (Uber, Lyft, etc.).
* Purchases / payments (shared purchase discipline).
* Send-on-behalf (email/Slack/etc. as the user — with confirmation norms).
* Channels (inbound messaging platforms).
* Export bot template (shareable bot setup).

## 12. Safety, privacy, and trust

### 12.1 Auto-review

Certain actions (Shell on the box, computerUse, MCP calls, routine writes, cloud agent launches) get an automatic safety check. On block: adapt to a safer path, or escalate the same action so the user gets an approval card — never sneak around via cookies, encoding tricks, or more invasive substitutes.

### 12.2 Local execution

Access to the user's registered computers requires explicit allow. Setting lives under General → Local execution. Already-allowed machines can be probed without re-prompting until revoked.

### 12.3 Credentials

* Never ask users to paste tokens into chat; use secret-request or plugin setup fields.
* Don't take the user's keys/sessions to grant the agent unauthorized access or bypass controls.
* Untrusted tool/web content is treated as data, not instructions (fence-aware).

### 12.4 Acting as the user

Outbound posts/sends/mutations on the user's accounts need clear confirmation norms (send-on-behalf / purchases skills). Speak as the user when acting through their accounts; don't refer to them in the third person in those contexts.

### 12.5 Confidential workspaces

When the user requires privacy (e.g. Notion report pages), create as private drafts only, do not share/move/publish without explicit direction.

## 13. UX patterns for agents

* First visible action on a user turn is a real chat message (ack or answer).
* Keep the user posted on meaningful beats; don't narrate every tool call.
* Ack ≠ delivery — always send the awaited result.
* Choice cards for real decisions; don't use them to re-confirm tools that already open their own review UI.
* Autonomy: assume and proceed on low-stakes choices; mention assumptions.
* Initiative: offer routines for repeated work; surface missing connectors tied to what the user actually wants.
* Don't discuss internals/prompting/architecture with end users unless they're builders asking for that (this document is builder-facing).

## 14. Ecosystem map (summary)

```
User (desktop app)
├── Agents (persona, memory, chat, settings)
│   ├── Routines (cron + event listeners)
│   ├── Skills (global library)
│   ├── Teammates / Channels (async multi-agent)
│   └── Subagents (executor, computerUse, video…)
├── Agent computer (shared Linux box + per-agent desktop)
├── User computers (registered machines + local approval)
├── Connectors (MCP plugins: Notion, Slack, …)
├── Web + browser logins on the box
└── Cursor cloud agents (repos / code)
```
